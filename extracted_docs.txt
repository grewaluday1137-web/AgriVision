1. Executive Summary
SOURCE REQUIREMENT / SRS POSITION
AgriVision AI is a web-based decision-support platform with three independent AI-powered services: plant disease detection from a leaf image, smart crop recommendation from soil and weather values, and crop yield prediction from a final dataset-supported schema.
RECOMMENDED IMPLEMENTATION DETAIL
The recommended product shape is a responsive React frontend, a Python FastAPI backend, PostgreSQL for application records, and three versioned inference artifacts. Each module can be deployed behind one API while retaining a separate validation and model lifecycle.
The system is intended to make agricultural information easier to access, not to replace agronomic assessment, field inspection, laboratory testing, or local crop-management advice. Every result must be presented as a model output with its relevant limitations.
A user begins at a dashboard, chooses a service, supplies only the input that the corresponding trained model supports, receives a clearly labeled result, and may view a history record where that optional capability is enabled. The backend validates the request, invokes exactly one relevant model, formats the result, optionally stores a record, and returns a safe response.

Success Condition
The project is functionally complete when each of the three services accepts a valid, supported request; uses a documented and versioned model artifact; returns an understandable response; handles invalid or unavailable dependencies without fabricating a result; and is connected to the frontend. Any optional account, history, or administration feature is complete only when explicitly included in the final release scope.
2. Scope, Objectives, and Product Boundaries
SOURCE REQUIREMENT / SRS POSITION
The SRS objectives are to detect common plant diseases, recommend suitable crops from soil and weather parameters, predict crop yield from agricultural data, provide a user-friendly web interface, display results clearly, provide basic guidance, and retain a modular architecture.
RECOMMENDED IMPLEMENTATION DETAIL
The initial release should maintain a narrow, demonstrable boundary: model-backed predictions, curated guidance, validation, version traceability, and an interface that explains what the result does and does not mean.
In-Scope Capabilities
A landing page and dashboard that expose the three services as independent workflows.
Leaf-image upload, safe image validation, preprocessing, disease classification, result rendering, and curated disease guidance.
A crop recommendation form containing nitrogen, phosphorus, potassium, temperature, humidity, pH, and rainfall values.
A yield form generated from the final selected model schema rather than a speculative universal list of agricultural fields.
REST interfaces for health, the three predictions, history where enabled, and guidance retrieval.
Optional prediction history and optional administrator functions, with privacy controls when accounts exist.
Explicitly Outside Mandatory Initial Scope
Area
Boundary
Additional trained models
No image-quality model, weather model, recommendation ensemble, chat model, or separate guidance model is part of the initial three-model limit.
Live integrations
Weather APIs, soil sensors, government services, satellite or drone imagery, and location intelligence are future possibilities, not initial requirements.
Delivery channels
A native mobile app and downloadable prediction reports are future enhancements unless deliberately added to the implementation scope.
Guarantees
The system does not guarantee disease diagnosis, crop suitability, farm profitability, or realized yield.
Professional advice
Curated guidance is informational. It must not be presented as a substitute for a qualified local agronomist or plant-health professional.
System Boundary
AgriVision AI owns the browser experience, API validation, model invocation, result formatting, optional account and history records, model version references, and curated guidance records. It does not own the underlying weather, soil, crop-production, or image datasets. Training datasets are governed by their source and license terms; production operation uses only the selected exported artifacts and their documented preprocessing assets.
3. Requirements Traceability and Model-Governance Constraint
SOURCE REQUIREMENT / SRS POSITION
The initial application shall contain a maximum of three trained machine learning models. Only one selected algorithm or trained model is deployed for each task. Alternatives may be compared during experimentation.
RECOMMENDED IMPLEMENTATION DETAIL
Model selection and deployment should be governed by a model registry, a release checklist, and a hard deployment check that prevents a fourth production inference artifact from being registered as a user-facing model.
OPEN DECISION / CONFIRM BEFORE BUILD
The label ResNet-99-2 is source-supplied but does not define a universally identifiable architecture, layer configuration, weights source, input dimensions, license, framework, or preprocessing. The project must record the exact code implementation, architecture definition, class map, input transform, and artifact checksum before model training or inference begins.

5. Functional Architecture and End-to-End Flow
SOURCE REQUIREMENT / SRS POSITION
The SRS describes a web frontend, a FastAPI backend, a PostgreSQL database, three machine-learning components, and optional history/administration capability. Frontend and backend communicate through REST APIs.
RECOMMENDED IMPLEMENTATION DETAIL
Use a layered architecture that isolates user-interface code, HTTP validation, application orchestration, inference adapters, persistence, and curated guidance. This makes models replaceable without rewriting every screen or endpoint.

Canonical Request Lifecycle
1. The browser submits a module-specific request over HTTPS. 2. The API assigns a correlation identifier, authenticates if required, applies size and shape controls, and parses the input. 3. The module service validates model-domain constraints. 4. The appropriate inference adapter applies the release-specific preprocessing and runs exactly one selected model. 5. The service resolves curated guidance only after a supported disease key is available. 6. A response is built from declared fields, optionally persisted to history, and returned with safe warnings. 7. Errors are logged with the correlation identifier without exposing stack traces or sensitive values to the user.
Independence of the Three Services
The three services share platform capabilities such as validation, observability, model metadata, and optional history. They do not depend on one another for a prediction. A crop recommendation request cannot require a disease result, and a yield request cannot assume crop-advisor output unless an explicitly designed future workflow obtains user confirmation and the yield model supports the transferred value.

The SRS requires each model to have a documented input and output format, tracked model versions, modular code, and maintained API documentation.
RECOMMENDED IMPLEMENTATION DETAIL
Implement each deployed model as a self-contained release package with a manifest, immutable artifact reference, preprocessing specification, supported-domain declaration, output mapping, and evaluation link. The runtime should call the package through a stable adapter interface.

Shared Adapter Interface
A module adapter should accept a validated application request and an active release manifest, then return a typed domain result. Its internal behavior is: validate final contract; transform input with release-owned preprocessing; invoke the model; convert raw output to declared semantics; attach model identifier/version; return warnings about support limits. This interface prevents route code from containing model-specific feature orders, classes, or thresholds.
Training/Serving Parity
The production service must reuse the same logical transformations that were fitted or defined during training. Examples include categorical encoding, feature ordering, scaling, missing-value treatment, image resizing, normalization, and class-label mapping. Reimplementing these transformations separately in frontend code or ad hoc request handlers creates a high risk of silent inconsistency.
Runtime Model Loading
Load and validate each selected artifact at service startup or through a controlled lazy loader with a readiness check.
Expose model readiness internally and through a restricted health/readiness view; do not publish artifact paths, secrets, or raw diagnostic traces.
Fail closed if the active artifact, manifest, or required preprocessing component is missing or incompatible.
Use an explicit release-selection setting rather than falling back automatically to an old or experimental artifact.
Record the released model version with every history record and in operational logs.
7. Plant Disease Detection: Plant Doctor
SOURCE REQUIREMENT / SRS POSITION
The system shall accept an uploaded leaf image, validate image type and size, preprocess it, classify it with the trained disease model, display the predicted class and confidence, provide related guidance where available, and show an understandable error when processing fails. The final SRS addendum selects ResNet-99-2.
RECOMMENDED IMPLEMENTATION DETAIL
Use a multipart upload endpoint backed by a strict file-validation service. Treat the disease classifier as a closed-set model: it can classify only the healthy/disease classes represented in its final training label map and must not be described as universal plant diagnosis.
OPEN DECISION / CONFIRM BEFORE BUILD
Confirm the exact meaning and provenance of ResNet-99-2, the machine-learning framework, class-label mapping, image input transform, and whether any external evaluation dataset is permitted and suitable for this academic project.
Input Contract

Inference Pipeline
Receive multipart upload and generate a correlation identifier before any processing.
Reject an absent, oversized, unsupported, malformed, unreadable, or decompression-risk image with a controlled validation response.

Result Presentation
Result element
Required behavior
Predicted condition
Display the supported class label without claiming laboratory or expert confirmation.
Confidence
Label as model confidence. Explain that a high score reflects the model distribution and does not guarantee correctness in a real field image.

Dataset and Evaluation Discipline
The named dataset is the New Plant Diseases Dataset, with PlantDoc named as an optional external evaluation dataset. Dataset availability, license, class coverage, duplicates, split leakage, label semantics, and real-field representativeness must be inspected before training. The SRS identifies accuracy, precision, recall, F1-score, and a confusion matrix as evaluation outputs, but it does not supply achieved scores. The final report must present measured results by release, not targets disguised as outcomes.

Processing Pipeline
Parse the JSON body and reject missing fields, non-numeric values, non-finite values, and duplicate/conflicting fields.

Interpretation and Guardrails
The recommendation is a dataset-backed classification result. It does not account automatically for local seed availability, irrigation, pest pressure, market conditions, farm management, regulatory constraints, recent laboratory results, or climate anomalies unless such variables are actually part of the model contract. The result screen should say this in concise user-facing language.
9. Crop Yield Prediction: Yield Forecaster
SOURCE REQUIREMENT / SRS POSITION
The yield module shall process the required agricultural parameters through an XGBoost Regressor, display an estimated yield and corresponding unit, and notify users when inputs fall outside the supported model range. The final fields and unit must match the selected yield dataset.
RECOMMENDED IMPLEMENTATION DETAIL
Build this module from a machine-readable feature manifest generated during training. Do not hard-code a speculative yield form. The frontend should render the active fields, units, type constraints, categorical options, and help text from a controlled configuration derived from the artifact.
OPEN DECISION / CONFIRM BEFORE BUILD
Inspect the final yield dataset before finalizing API fields, database retention, UI labels, units, categorical choices, missing-data policy, and validation bounds. This is a release-blocking decision.

Known from source
Must be discovered from selected data/training

Exact input columns, target column, yield unit, location coverage, time coverage, supported categories, missing-value treatment, and any feature encodings.
Candidate concepts include crop type, location/region if supported, season, year where available, cultivated area, historical agricultural data, and weather/soil features where available.
Whether each candidate concept exists in the dataset and is permissible for inference.

Manifest-Driven Form Behavior
A field definition declares display label, API key, data type, unit/help text, required status, supported categories or numeric bounds, and privacy classification.
The client loads the active contract at build time or through a controlled configuration endpoint; it must not expose internal artifact paths or training data.
The backend remains authoritative: it revalidates every field and rejects extra or missing features unless a documented compatibility policy says otherwise.
Categorical encodings are applied server-side by the trained pipeline. The browser sends an allowed business value, not an ordinal number invented by the UI.
Prediction Pipeline
Validate that the request matches the active release schema exactly enough for safe inference.
Normalize user-provided units only when a verified and documented conversion is supplied; otherwise require the declared unit.
Apply the release-owned encoding, missing-value behavior, feature selection, and feature ordering.
Run the XGBoost regressor and return the numeric estimate with the model-declared unit and model version.
Warn or decline when the input is outside policy-defined supported domain. Do not present a false precision or a guaranteed harvest quantity.
Result Interpretation
Yield is influenced by factors that may not be captured by the selected historical dataset. The result must be phrased as an estimate from the model's represented data context. Avoid currency, profit, harvest date, or actionable input recommendations unless they are separately supported by the documented scope and data.
10. Data Lifecycle, Training, and Evaluation Pipeline

The SRS requires duplicate detection, missing-value handling, data-type validation, feature selection, categorical encoding where needed, scaling where required, image resizing/normalization, train-validation-test splitting, and appropriate evaluation.
RECOMMENDED IMPLEMENTATION DETAIL
Treat notebooks as exploratory evidence, not the release system. Use repeatable data-preparation and training jobs that produce versioned manifests, artifacts, evaluation reports, and an auditable relationship between input data and output model.

Disease-Model Training Flow
For leaf images: inventory classes and healthy labels; inspect duplicates and label quality; define a split that avoids leakage; implement the confirmed ResNet-99-2 architecture; apply training transforms separately from deterministic inference transforms; train with reproducible configuration; evaluate on held-out images; optionally evaluate on an external domain only if the data is suitable; inspect confusion patterns; export weights, class map, inference transform, and report as a single release.
Crop-Recommendation Training Flow
For crop recommendation: load the seven expected feature concepts and crop label; verify data types and units; profile missingness and range; decide documented handling for invalid/missing records; select the one final classifier after comparison; fit any required pipeline on the training portion; evaluate against a stratified held-out set as required by the SRS; inspect per-class behavior; export the selected model with feature order and label map.
Yield-Model Training Flow
For yield prediction: first determine the actual dataset target and its unit. Build a schema contract from verified columns, identify time/location leakage risks, encode categories and handle missing values with train-only fitting where applicable, define a defensible hold-out strategy, train the proposed regressor, report MAE, RMSE, and R-squared on unseen records, and export the exact preprocessing plus unit metadata. The evaluation report must explain whether a metric is appropriate to the target scale and dataset distribution.

Yield Contract Discovery
The yield endpoint must reject requests that do not match the deployed feature manifest. Idempotency, Timeouts, and Side Effects
Prediction endpoints should be treated as read-like computations even if an optional history row is created. A client retry can otherwise create duplicate history records.
Use a client request identifier or server-issued correlation ID to deduplicate a short retry window where history is enabled.
Bound upload/read time, preprocessing time, and inference execution time. A timeout must return a controlled unavailable result and must not cache a partially computed response.
Persist a prediction only after the model response is complete and valid, unless a deliberate audit policy records failed requests separately.

Error Contract Rules
Errors should distinguish validation, authentication/authorization, unavailable dependency, conflict/duplicate, and unexpected server failure. The API must use stable machine-readable codes so the frontend can render a useful message without matching on prose. A response never includes tracebacks, filesystem paths, raw database messages, or a prediction generated from an incomplete pipeline.
Fallback Policy
There is no acceptable inference fallback that adds another user-facing model or guesses a result. If the active disease model is unavailable, Plant Doctor is unavailable. If crop/yield artifacts are unavailable or incompatible, their module is unavailable. Guidance is the only independent content path and cannot replace a missing model result.

Final Principles
AgriVision AI is strongest when it is explicit about what it knows: it accepts only supported inputs, runs exactly the selected three models, displays outputs with their units and limitations, separates curated guidance from machine learning, protects user data when optional accounts/history exist, and records enough release information to reproduce or responsibly withdraw a result.
The final build should be judged by evidence: documented dataset inspection, reproducible preprocessing, actual evaluation reports, safe API behavior, accessible frontend workflows, controlled failure states, and an honest account of scope. Those practices preserve the SRS intent while making the system technically credible and maintainable.
